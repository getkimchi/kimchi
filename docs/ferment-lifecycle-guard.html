1. What is a Ferment?

A Ferment is Kimchi's structured unit of work for complex, multi-step coding tasks. Instead of letting the AI model wander freely through a codebase, a Ferment enforces a state machine: the model must progress through defined lifecycle stages, and at each stage the engine derives what action is needed next. The model is expected to call a specific tool to advance the state — it cannot skip ahead or improvise transitions.

Think of it like a project plan with phases and steps. The model acts as the engineer executing the plan, but the harness (Kimchi) tracks the state and tells the model what the next action is. If the model forgets to call the right tool, the harness nudges it.

💡 Key concept
The Ferment state machine is persistence-backed: every transition is written to a JSON file on disk. The in-memory "what should the model do next?" decision is derived from this persisted state via a pure function determineNextAction(ferment). The guard this fix introduces sits between that derivation and the model's next opportunity to act.

3. Lifecycle Actions & Expected Tool Calls

The engine's determineNextAction(ferment) function inspects the persisted state and returns a declarative action — a description of what should happen next. Each action maps to a specific tool the model is expected to call:

Action Tool the model must call When it's needed Concrete?
scope scope_ferment Ferment is a draft with no phases yet ✓ one tool
activate_phase activate_ferment_phase Ferment is planned, no phase is active ✓ one tool
refine refine_ferment_phase Active phase has no steps yet ✓ one tool
start_step start_ferment_step Active phase has a pending step ✓ one tool
complete_step complete_ferment_step A step is running and its worker has finished ✓ one tool
complete_phase complete_ferment_phase All steps in the active phase are done ✓ one tool
complete_ferment complete_ferment All phases are completed/skipped ✓ one tool
recover_step choice: skip or restart A step has failed ⚠ multiple options
recover_phase choice: retry, skip, or abandon A phase has failed ⚠ multiple options
pause no tool Ferment is paused or drifted — no action
Concrete vs. choice-oriented
Most actions map to exactly one tool — these are "concrete obligations." But recover_step and recover_phase have multiple valid paths (skip the failed item, retry it, or abandon the ferment). These are "choice-oriented" — the guard must prompt the model to act without claiming one specific tool is mandatory.

  • The guard does not fire here — it would interrupt legitimate conversation

5. The Problem: Silent Stalls

In automated mode, the model sometimes ends its turn with a text-only response (no tool calls) while the Ferment still requires a lifecycle transition. The most common pattern:

🐛 The bug — "Calling scope_ferment now"

The model produces prose announcing its intent to call a tool, but the actual toolCalls array is empty and stopReason is "stop". The model thinks it called the tool, but it didn't. 

// Model response — looks like it's about to call scope_ferment...
{ content: [{ type: "text", text: "Calling scope_ferment now." }],
  stopReason: "stop",
  toolCalls: [] }  // ← no actual tool call!

What happened before the fix

The old recovery mechanism (maybeInjectReactiveContinuationNudge) had three problems:

  1. Budget of 1 — only one retry was allowed (MAX_CONSECUTIVE_REACTIVE_NUDGES = 1). After the model's second text-only stop, the budget was exhausted and the session ended silently.
  2. Keyed by Ferment ID only — the retry counter was a simple Map<fermentId, count>. When the Ferment advanced to a new lifecycle stage (e.g. from scope to activate_phase), the old counter was not automatically reset. Worse, any tool call — even an unrelated read or grep — reset the counter via onFermentToolCallSeen, silently replenishing the budget for an unchanged obligation.
  3. No exhaustion diagnostic — when the budget ran out, the session simply disappeared. No breadcrumb, no telemetry, no indication of what went wrong.

Reactive nudge fires (budget 0→1)
The old nudge injects a continuation message. Model gets another turn.

6. Root Cause Analysis

The old design had a fundamental mismatch: it tracked how many times the model stopped per Ferment, but not what obligation was unmet. This led to two failure modes:

Problem 1: Budget too small

With MAX_CONSECUTIVE_REACTIVE_NUDGES = 1, the model got exactly one retry. If it failed twice in a row (which is common — the "Calling scope_ferment now" pattern repeats), the session died.

Problem 2: Wrong key

The counter was keyed by fermentId only. It didn't distinguish between different obligations (scope vs. activate_phase vs. start_step). Any tool call reset it, even tools unrelated to the pending obligation. State advancement didn't automatically grant a fresh budget.

⚠ Conflated paths
The old code also used maybeInjectReactiveContinuationNudge for both stopReason: "stop" (model chose to stop) and stopReason: "error" (transport/provider failure). These are fundamentally different failure modes that should have separate recovery budgets — a network error is not the model's fault and shouldn't consume the lifecycle retry budget.

7. The Fix: Lifecycle Obligation Guard

The fix replaces the old reactive nudge with a new module: src/extensions/ferment/lifecycle-obligation-guard.ts. It introduces three key changes:

7.1 Obligation-keyed retry budget

Instead of keying by Ferment ID alone, the guard keys retries by the specific outstanding obligation: 

obligation key = fermentId + ":" + action.kind + ":" + phaseId? + ":" + stepId?

Examples:

ScenarioObligation Key
Draft ferment needs scopingferment-123:scope
Planned ferment needs first phase activatedferment-123:activate_phase:phase-1
Running ferment needs step startedferment-123:start_step:phase-1:step-2
Failed step needs recoveryferment-123:recover_step:phase-1:step-1
✓ What this fixes
  • An unrelated read/grep call does not reset the budget — the key is unchanged.
  • When scope_ferment succeeds, state advances to activate_phase, which has a different key → fresh budget automatically.
  • Switching to another phase or step produces a new key → fresh budget.
  • Old keys for a Ferment are pruned when a new current key is observed, so the map doesn't grow indefinitely.

7.2 Budget of 2 retries

The model now receives three total opportunities for one unchanged obligation:

7.3 Exhaustion diagnostic

When the budget is exhausted, the guard emits one visible breadcrumb explaining what happened, plus a FERMENT_EVENTS.STALLED telemetry event. The persisted state is left intact — no state is fabricated or silently skipped. 

Lifecycle guard exhausted for "Hello World CLI":
required action "scope" (tool: scope_ferment) was not called after 2
lifecycle-stop retries (3 qualifying text-only stops for the unchanged
obligation). No state transition was applied automatically.
📝 Wording note
The message says "qualifying text-only stops for the unchanged obligation" rather than "consecutive text-only stops." This is deliberate: an unrelated tool call between stops does not reset the budget, so the stops may not be consecutive. The wording accurately reflects what was counted.

10. Handling Recovery Actions

recover_step and recover_phase are special: they don't map to one mandatory tool. A failed step can be skipped (skip_ferment_step) or retried (start_ferment_step). A failed phase can be retried, skipped, or the ferment can be abandoned. The guard must not claim one exact tool is mandatory.

🐛 Bug found during review (fixed in this branch)
The initial implementation excluded recover_step/recover_phase from the guard entirely — returning undefined from deriveObligation. This meant a text-only stop during failure recovery would silently stall the run in automated mode — the exact bug class being fixed. The old reactive nudge had passed these actions to the scheduler, which provided choice-oriented guidance. The initial fix dropped that behavior.
✓ Fix: choice-oriented obligations
Recovery actions are now classified as choice-oriented obligations — they go through the same bounded retry tracker, but the guard does not name one mandatory tool. Instead, it schedules the existing scheduler guidance (which already lists the valid options) with a recovery-specific prefix.

The LifecycleObligation type uses a discriminated union:

type LifecycleObligation =
  | { mode: "concrete";          toolName: string;  action: ConcreteLifecycleAction }
  | { mode: "choice-oriented";   toolName?: never;   action: ChoiceOrientedLifecycleAction }

For choice-oriented obligations:

  • Retry message: "Diagnose the failure and choose an appropriate recovery path from the guidance below." (no tool named)
  • Scheduler guidance: The existing buildContextualNudge produces: "Use skip_ferment_step or restart the step via start_ferment_step after fixing the issue."
  • Exhaustion message: "required recovery action 'recover_step' remained unresolved" (no tool named)
  • Same budget: 2 retries, keyed normally (e.g. ferment-1:recover_step:phase-1:step-1)

11. Error vs. Stop Separation

The old code used maybeInjectReactiveContinuationNudge for both stopReason: "stop" and stopReason: "error". These are fundamentally different:

stopReason: "stop"

  • The model chose to stop
  • It could have called a tool but didn't
  • Recovery: nudge the model to try again
  • Consumes the lifecycle-stop retry budget

stopReason: "error"

  • Transport/provider/gateway failure
  • The model never got to respond
  • Recovery: schedule another turn directly
  • Does NOT consume the lifecycle-stop budget

After the fix, the stopReason: "error" path in events.ts clears the guard budget (so the error doesn't contaminate future lifecycle-stop tracking) and then schedules a continuation turn independently via scheduleNextFermentAction. The two paths are fully separated.

12. Key Design Decisions

Why automated-only?

In interactive mode, a text-only stop may be legitimate — the model might be explaining trade-offs or asking the user a question. Firing a lifecycle nudge would interrupt the conversation. The user is present to steer, so the guard is not needed. Interactive coverage is deferred until the harness can reliably distinguish legitimate conversation stops from lifecycle stalls.

Why session-memory, not persisted?

The retry counter lives in an in-memory Map, not in the Ferment event store. This is an agent-loop recovery budget, not domain progress. Persisting it would mean replaying the budget on session restart, which could cause stale exhaustion states. The existing nudge counters follow the same pattern.

Why not force the tool call?

The guard never applies a state transition itself. It only schedules another model turn via scheduleNextFermentAction (steer delivery). The model must still produce the tool call — the tool's own validation logic persists the transition. This preserves the domain model: 

persisted Ferment state
        ↓
determineNextAction / continuation policy
        ↓
declarative lifecycle obligation  ← guard lives here
        ↓
model emits corresponding lifecycle tool call
        ↓
tool validates and persists the transition

Why prune old keys?

A long-running Ferment may progress through many phases and steps, each producing a different obligation key. Without pruning, the per-Ferment map would grow unboundedly. When a new current key is observed, all old keys for that Ferment are deleted. This keeps memory usage bounded regardless of Ferment length.

Why a discriminated union for the obligation type?

Using mode: "concrete" | "choice-oriented" with toolName: string vs toolName?: never makes the "no prescribed tool" state explicit at the type level. You literally cannot set a tool name on a choice-oriented obligation — the compiler enforces it. This prevents accidentally naming a mandatory tool for a recovery action.
