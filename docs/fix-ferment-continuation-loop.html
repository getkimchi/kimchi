Fix: Ferment Continuation Loop

Trace: 2026-07-14T16_19_00Z-continuation-loop.jsonl · Session 0.1.65 · Model: glm-5.2-fp8

Problem

An interactive TUI session with a stale "automated" continuation policy (left over from a previous ferment where the user chose "Start execution in auto mode") fell into a 16-turn, 90-second "Acknowledged / Standing by" text-only loop after propose_ferment_scoping returned "Plan ready for review" and the plan review dialog was shown to the user.

Two independent nudge systems — one in the ferment extension, one in the orchestration layer — each failed to check whether a plan review was pending, and together they ping-ponged the session into an infinite continuation loop that the user could not ESC out of.

Bug 1: scheduleNextFermentAction doesn't check for pending plan reviews

File: src/extensions/ferment/scheduler.ts

Current logic — step by step

Step 1

scheduleNextFermentAction(pi, ferment, runtime, opts) is called from multiple paths: maybeInjectReactiveContinuationNudge, maybeInjectFermentStopNudge, auto-compaction continuation, and scheduleFermentWakeUp.

Step 2

The function refreshes the ferment from storage and checks terminal states:

const ferment = runtime.getStorage().get(scheduledFerment.id) ?? scheduledFerment
if (ferment.status === "complete" || ferment.status === "abandoned" || ferment.status === "paused") {
    if (ferment.status === "complete" || ferment.status === "abandoned") runtime.setActive(undefined)
    else runtime.setActive(ferment)
    return
}

Only complete, abandoned, and paused are terminal. A draft ferment passes through.

Step 3

The function calls decideContinuation to get the next action:

const decision = decideContinuation(ferment, runtime.getContinuationPolicy(), opts)
if (decision.type !== "continue") return
const action = decision.action

For a draft ferment, decideContinuation returns { type: "continue", action: { kind: "scope", ... } } — meaning "the model should do scoping next".

Step 4 — THE BUG

The function calls shouldSuppressHiddenNudge to decide whether to suppress the nudge:

if (shouldSuppressHiddenNudge(action, runtime.getContinuationPolicy())) return

shouldSuppressHiddenNudge only checks the action kind and policy:

function shouldSuppressHiddenNudge(action: DeclarativeAction, policy: ContinuationPolicy): boolean {
    if (action.kind === "scope") return policy !== "automated"
    return false
}

When the policy is "automated", scope nudges are never suppressed — by design, because in headless one-shot mode the nudge is the only thing keeping the session alive during draft scoping. But this is wrong when the session is interactive TUI with a stale automated policy and a plan review dialog is about to be shown.

Step 5

The nudge is sent via safeSendMessage with triggerTurn: true, which creates a new turn:

safeSendMessage(pi, {
    customType: "ferment_continuation_nudge",
    content: [{ type: "text", text: messageText }],
    display: false,
    details: { action: action.kind },
}, { triggerTurn: true })
Result

Even though propose_ferment_scoping set pendingPlanReview and the ferment turn_end handler correctly returns early when hasPendingPlanReview(runtime) is true, the nudge fires from a code path that doesn't check for pending plan reviews. The trace confirms: at 16:15:16.636Z, a "Reactive continuation nudge [scope]" breadcrumb fires with "policy automated" — 11 seconds after propose_ferment_scoping set the pending review.

Fix 1: Guard scheduleNextFermentAction against pending plan reviews

File: src/extensions/ferment/scheduler.ts · Function: scheduleNextFermentAction

Add a hasPendingPlanReview check early in scheduleNextFermentAction, after the terminal-state check and before decideContinuation:

export function scheduleNextFermentAction(
    pi: ExtensionAPI,
    scheduledFerment: Ferment,
    runtime: FermentRuntime,
    opts: ScheduleNextFermentActionOptions = {},
): void {
    const ferment = runtime.getStorage().get(scheduledFerment.id) ?? scheduledFerment
    if (ferment.status === "complete" || ferment.status === "abandoned" || ferment.status === "paused") {
        if (ferment.status === "complete" || ferment.status === "abandoned") runtime.setActive(undefined)
        else runtime.setActive(ferment)
        return
    }

    // ── NEW: suppress nudges when a plan review is pending ──────────
    // When propose_ferment_scoping returns "Plan ready for review", the host
    // defers the review dialog to agent_end. Any nudge here would start a new
    // turn, preventing agent_end from firing and the dialog from appearing.
    // This guard is the single chokepoint for ALL ferment nudge paths:
    // reactive continuation, stop nudge, auto-compaction continuation, and
    // scheduleFermentWakeUp all funnel through scheduleNextFermentAction.
    if (hasPendingPlanReview(runtime)) return

    runtime.setActive(ferment)

    const decision = decideContinuation(ferment, runtime.getContinuationPolicy(), opts)
    // ... rest unchanged

Why this works: hasPendingPlanReview checks runtime.getPendingPlanReview(activeId) !== undefined. When a plan review is pending, the ferment is in draft status and the review dialog hasn't been shown yet (or was shown and dismissed). Suppressing the nudge here lets the turn end naturally, which lets agent_end fire, which lets runPendingPlanReview show the dialog. Once the user confirms or cancels, clearPendingPlanReview is called, and subsequent nudges are no longer suppressed.

Why shouldSuppressHiddenNudge is the wrong place: That function is a policy-level check (manual vs. automated) that intentionally allows scope nudges in automated mode. The pending-plan-review check is a state check that applies regardless of policy — even in headless one-shot mode, you don't want to nudge while a review is pending (the headless path uses confirmPendingScope directly and never sets pendingPlanReview, so the guard is a no-op there).

Import needed: Add import { hasPendingPlanReview } from "./tool-scope.js" to scheduler.ts.

Bug 2: Orchestration ContinuationNudge doesn't check ferment state

File: src/extensions/prompt-construction/prompt-enrichment.ts · turn_end handler at ~line 375

Current logic — step by step

Step 1

The orchestration extension registers a turn_end handler that runs on every assistant turn, independently of the ferment extension's own turn_end handler. Both handlers run — they are not mutually exclusive.

Step 2

The handler first checks delegation tracking and the empty-turn nudge:

pi.on("turn_end", async (event) => {
    if (event.message.role !== "assistant") return
    const assistantMsg = event.message as AssistantMessage

    bumpStallCounter()

    // Mark delegation calls
    for (const c of assistantMsg.content) {
        if (c.type === "toolCall" && isDelegationToolCallName(c.name)) {
            continuationNudge.markDelegationCall()
        }
    }
Step 3

If the model's previous turn was a nudge response, check for done signal or intentional stop:

if (continuationNudge.isNudgeResponsePending()) {
    if (continuationNudge.isDoneSignalReceived() || assistantMsg.stopReason === "stop") {
        return  // respect the stop
    }
    // fall through to evaluateTurn
} else if (!continuationNudge.hasToolBeenCalledThisRun() && emptyTurnNudge.evaluateTurn(assistantMsg)) {
    pi.sendMessage({ customType: NUDGE_CUSTOM_TYPE, content: EMPTY_TURN_NUDGE_TEXT, display: false },
        { deliverAs: "followUp" })
    return
}
Step 4 — THE BUG

The handler calls continuationNudge.evaluateTurn(assistantMsg) without checking whether a ferment plan review is pending:

if (!continuationNudge.evaluateTurn(assistantMsg)) return
pi.sendMessage({
    customType: NUDGE_CUSTOM_TYPE,
    content: continuationNudge.getNudgeText(),
    display: false,
}, { deliverAs: "followUp" })

evaluateTurn checks: nudgeCountThisCycle < 2, toolsCalledThisSession, toolsCalledSinceLastUserInput, pendingDelegationCount, stopReason, and whether the message has text but no tool calls. It does not check any ferment state.

Step 5 — Cycle counter never resets

The cycle counter nudgeCountThisCycle is only reset by resetForNewUserInput(), which fires on input events with source !== "extension". But ferment nudges arrive as followUp / steer messages, which trigger input with source: "extension" — so clearDelegationPending() runs but resetForNewUserInput() does not.

pi.on("input", async (event) => {
    if (event.source === "extension") {
        continuationNudge.clearDelegationPending()
        return  // ← does NOT reset cycle counter
    }
    continuationNudge.resetForNewUserInput()
    emptyTurnNudge.resetForNewUserInput()
})
Result

After the ferment nudge fires (Bug 1), the model responds with text-only "Acknowledged" (stopReason: stop). The ferment turn_end handler correctly returns early (if hasPendingPlanReview is still true) or suppresses its own nudge (after 1 turn). But the orchestration turn_end handler fires evaluateTurn independently, injects a nudge followUp, and creates another turn. This repeats until both nudge budgets are exhausted — but by then, enough turns have passed that intermediate state changes may reset the ferment nudge counter, restarting the cycle.

Why this works: When a plan review is pending, the only thing the system should do is let the turn end naturally so agent_end fires and runPendingPlanReview can show the dialog. Bug 3: Continuation policy persists across ferments in the same session

File: src/extensions/ferment/index.ts · runPendingPlanReview at line 189

Current logic — step by step

Step 1

At session start, the continuation policy is set based on UI availability:

pi.on("session_start", async (_event, ctx) => {
    runtime.setContinuationPolicy(ctx?.hasUI ? "manual" : "automated")
    // ...
})

This correctly sets "manual" for interactive TUI sessions and "automated" for headless sessions. But this only fires once — at session start.

Step 2

When the user selects "Start execution in auto mode" from the plan review dialog, the policy is switched to "automated":

// In runPendingPlanReview, after confirmPendingScope:
if (outcome.kind === "start_auto") {
    runtime.setContinuationPolicy("automated")
    requestSharedStatusLineRender()
}

This is correct for the ferment the user is approving — they explicitly chose auto mode.

Step 3 — THE BUG

When the first ferment completes and a new ferment is created (e.g., the user starts a new task via /ferment new or the model bootstraps a draft), the continuation policy is not reset. The session_start handler doesn't fire again (the session is still running), and nothing in the ferment creation path resets the policy.

In the trace, the user selected "Start execution in auto mode" for the first ferment at 13:13. The first ferment completed at ~13:28. The second ferment ("Wire in the newly added variables...") was created hours later, but the policy was still "automated".

Result

The second ferment ran under "automated" continuation policy in an interactive TUI session. This caused shouldSuppressHiddenNudge to return false for scope actions, isAutomatedContinuationEnabled() to return true, and the reactive continuation nudge system to be active — all of which are only appropriate for headless one-shot mode.

Fix 3: Reset continuation policy when a new ferment is created

File: src/extensions/ferment/tools/lifecycle.ts · resolveProposeFermentTarget at ~line 480

When resolveProposeFermentTarget bootstraps a new draft ferment, reset the continuation policy to the session default. The session default is "manual" for interactive TUI and "automated" for headless — this can be determined from ctx.hasUI:

// In resolveProposeFermentTarget, after creating the new draft:
const f = storage.create(shortName, goal)
setActiveFermentAndApplyProfile(pi, runtime, f)

// ── NEW: reset continuation policy to session default for the new ferment.
// The previous ferment may have been in "automated" mode (user selected
// "Start execution in auto mode"), but that choice should not carry over
// to a new ferment. The session_start handler set the default based on
// ctx.hasUI; we replicate that logic here.
runtime.setContinuationPolicy(ctx.hasUI ? "manual" : "automated")

if (pi.events) {
    emitFermentCreated(pi.events, f)
}

Alternative: Reset the policy in setActiveFermentAndApplyProfile when the active ferment changes to a draft status ferment (indicating a new ferment is starting). But the resolveProposeFermentTarget location is more precise — it only fires on new ferment creation, not on every setActive call.

Note: The /ferment new command in commands.ts (line 288) already sets runtime.setContinuationPolicy("manual"). But resolveProposeFermentTarget is a separate creation path that the model uses when it calls propose_ferment_scoping with no ferment_id — this path was missing the reset.

How the three fixes work together

Before (broken)

  1. propose_ferment_scoping sets pendingPlanReview
  2. Model responds text-only (stopReason: stop)
  3. agent_end fires → runPendingPlanReview shows dialog
  4. User interacts with dialog → review is cleared
  5. Ferment nudge fires (Bug 1: shouldSuppressHiddenNudge allows scope nudges in automated mode, doesn't check pending review)
  6. Model responds "Acknowledged" (text-only, stop)
  7. Ferment nudge suppressed (cap=1) ✓
  8. Orchestration nudge fires (Bug 2: doesn't check pending review or ferment state)
  9. Model responds "Standing by" (text-only, stop)
  10. Orchestration nudge fires again (2nd of 2)
  11. Model responds "Acknowledged" (text-only, stop)
  12. Both nudge budgets exhausted... but turns keep happening
  13. Loop continues for ~16 turns until session is killed

After (fixed)

  1. propose_ferment_scoping sets pendingPlanReview
  2. Model responds text-only (stopReason: stop)
  3. Fix 2: Orchestration turn_end handler checks hasPendingPlanReview → TRUE → returns early. No nudge.
  4. agent_end fires → runPendingPlanReview shows dialog
  5. User interacts with dialog → review is cleared
  6. Fix 1: If any ferment nudge path is reached, scheduleNextFermentAction checks hasPendingPlanReview → still pending (or just cleared) → returns early if pending. If cleared, shouldSuppressHiddenNudge runs normally — but Fix 3 ensures the policy is "manual" for a new interactive ferment, so scope nudges are suppressed anyway.
  7. No nudges fire. Session waits for user input.
  8. If user confirms the plan → scheduleFermentWakeUp fires with deliverAs: "followUp" — but only after clearPendingPlanReview, so Fix 1 doesn't block it.

Defense in depth

The three fixes form a defense-in-depth strategy:

Fix Layer What it guards Without it
Fix 1 Ferment scheduler All ferment nudge paths (scheduleNextFermentAction) Bug 1 fires → first nudge injected → loop starts
Fix 2 Orchestration Orchestration ContinuationNudge in turn_end Bug 2 fires → loop sustains even after ferment nudge is suppressed
Fix 3 Ferment lifecycle Continuation policy on new ferment creation Stale "automated" policy makes scope nudges fire in interactive mode

Any single fix would prevent the loop in this trace, but all three are needed to prevent variants:

  • Fix 1 alone wouldn't prevent the orchestration nudge from firing if the pending review was cleared by the user (e.g., they cancelled the dialog) but the model kept responding with text-only turns.
  • Fix 2 alone wouldn't prevent the ferment nudge from firing — it only guards the orchestration path.
  • Fix 3 alone wouldn't help if the user explicitly chose "Start execution in auto mode" for the current ferment — that's a legitimate automated run where the nudge system should be active, but Fix 1 and Fix 2 still need to check hasPendingPlanReview to prevent nudging during the plan review phase.
